### Backend services ([ui/backend/services/](ui/backend/services/))

- **`optimizer_runner.py`** — `_run_live` (daemon thread; ask/tell loop; pushes SSE events to an `asyncio.Queue` via `run_coroutine_threadsafe`; `try/finally` always enqueues the `None` sentinel), `_run_replay` (drip-feeds checkpoint rows at 50 ms — **no** `try/finally`, see BUG-11), `_apply_overrides` (budget/algorithm/seed only), module-level `_runs` registry (never evicted, see BUG-13).
- **`score_service.compute_score`** — loops enabled specs; a spec with no supplied value is excluded from the aggregate (root of BUG-02).
- **`checkpoint_reader`** — CSV via `.iterrows()` (dotted columns like `point.score`); JSON via `Optimization_Log_Visualizer`.
- **`env_probe`** (ngspice + PDK → `/api/env`), **`netlist_parser`** (`.param` regex), **`yaml_generator`** (wizard form ↔ YAML).

### Library (`src/spicexplorer`)

- **`core/domains.py`** — `Project_Setup.from_yaml` via dacite (`strict=False`, so unknown/duplicate keys pass silently); `Param`, `TargetSpec`/`ListTargetSpec`, `tech_spec`/`pvt_map`/`pvt_corners`.
- **`core/utils.py`** — engineering-string parsing + the two error fns + the `<= 0` normalizing-coeff guard (bypassed by `nan`, BUG-07).
- **`spice_engine/spicelib.py`** (ngspice + param injection), **`optimization/orchestrator.py`** + **`base.py`** + **`stochastic/nevergrad.py`**.

### Key end-to-end flows

1. **Load/Apply** — SetupTab → `POST /api/project/load` (path or content) → `projectStore.apply(summary, yamlPath)`. *Content path returns `yaml_path=""` → BUG-03.*
2. **Live run** — OptimizeTab → `launchRun` → `POST /api/optimize/start` (`_apply_overrides`) → `_run_live` thread → SSE `/api/optimize/stream/{id}` → `runStore.onmessage`. *Error events dropped → BUG-09; onerror kills run → BUG-12.*
3. **Replay** — preset checkpoint → `_run_replay` drip → same SSE.
4. **Score shaping** — ScoreShapingTab → `POST /api/score` → `score_service`. *Sends one spec → BUG-02.*
5. **Sanity** — `POST /api/sanity-check` → one optimization step.
6. **Schematic** — SchematicTab → `/api/xschem/project` + `/file` + `/resolve` → `parser` → `SchematicViewer`. *resolve 404s under Docker → BUG-01.*
7. **Sensitivity** — DeviceInspector → `/api/spec/{name}/sensitivity`.

### BUG-01 · Schematic symbols all render as red "?" placeholders under Docker: PDK xschem libs and xschem binary absent, so /api/xschem/resolve 404s every symref

- **Area:** Schematic (xschem viewer) — backend symbol resolution
- **Location:** [ui/backend/routes/xschem.py:47-66](ui/backend/routes/xschem.py#L47-L66) (_pdk_xschem_dir / _xschem_share_dirs / _search_roots); culprit: docker/Dockerfile.backend:113-127 (PDK COPY omits libs.tech/xschem, no xschem install); placeholder render at [ui/src/components/schematic/SchematicViewer.tsx:174-183](ui/src/components/schematic/SchematicViewer.tsx#L174-L183)
- **Severity:** 🟠 major · **Confidence:** high
- **Symptom:** In the Schematic view a .sch loads (wires/labels show) but every device instance (e.g. sg13g2_pr/sg13_lv_nmos.sym, devices/ipin.sym — 197 instances in ota-improved.sch) renders as a red-bordered box with "?" instead of its symbol. Rendered correctly before, on the native PDK-equipped server.
- **Root cause:** The Docker backend image has no way to resolve xschem symbol references, so every device instance in the Schematic view renders as a red-bordered "?" placeholder. Traced end to end:

1. Symref shapes: examples/OTA/folded_cascode/ihp-sg13g2/xschem/ota-improved.sch references symbols only as `devices/*.sym` (xschem-share library) and `sg13g2_pr/*.sym` (PDK xschem library) — e.g. devices/ipin.sym, sg13g2_pr/sg13_lv_nmos.sym. No bare or sibling-resolvable refs.

2. Backend resolver ui/backend/routes/xschem.py:_search_roots (57-66) = [base .sch dir, _pdk_xschem_dir(), *_xschem_share_dirs()].
   - _pdk_xschem_dir (47-54) needs $PDK_ROOT/$PDK/libs.tech/xschem to exist. Dockerfile sets PDK_ROOT=/opt/pdk, PDK=ihp-sg13g2 (docker/Dockerfile.backend:119-120) but only COPYs libs.tech/ngspice/{models,.spiceinit,osdi} (lines 113-115). docker/pdk/ihp-sg13g2/libs.tech/ contains only ngspice and verilog-a (verified) — no xschem dir, zero .sym files — so /opt/pdk/ihp-sg13g2/libs.tech/xschem does not exist and _pdk_xschem_dir() returns None.
   - _xschem_share_dirs (16-44) needs shutil.which("xschem") on PATH OR $XSCHEM_LIBRARY_PATH. Dockerfile.backend installs no xschem binary (grep for "xschem" in the Dockerfile returns nothing) and neither the Dockerfile nor compose.yaml backend environment (compose.yaml:34-44) nor entrypoint-backend.sh sets XSCHEM_LIBRARY_PATH — so it returns [].
   - base .sch dir = the loaded file's own dir (examples/.../xschem/), which has no devices/ or sg13g2_pr/ subdir (no such dirs exist anywhere in the repo; only sibling files like ota-improved.sym).

3. So _search_roots collapses to just the .sch dir, none of the refs resolve, and /api/xschem/resolve raises HTTPException(404) at xschem.py:138 for every ref.

4. Frontend: [ui/src/lib/api.ts:194-199](ui/src/lib/api.ts#L194-L199) xschemResolve -> req() throws on !res.ok (api.ts:25-31). SchematicTab.tsx:79-95 catches per-ref and returns null (line 85), so the ref is omitted from symMap. SchematicViewer.tsx:147-183: symbols.get(inst.symref) is undefined, so the ternary at line 174 renders <SymbolPlaceholder/> (red box + "?", defined lines 482-508) for every instance.

This is a Docker-only regression (works on the native PDK-equipped server where the real PDK ships libs.tech/xschem — confirmed by examples/.../xschem/xschemrc:20 sourcing $PDK_ROOT/$PDK/libs.tech/xschem/xschemrc — and xschem is on PATH). Introduced by Dockerizing the xschem viewer (viewer added in commit 6cd1e53).
- **Fix direction (not implemented):** Give the backend container a way to resolve xschem symbols. Either vendor the symbol libraries into docker/pdk and the image, or ship a self-contained symbol set with the examples:
(1) Add docker/pdk/ihp-sg13g2/libs.tech/xschem/ (at least sg13g2_pr/*.sym) and COPY it into /opt/pdk/ihp-sg13g2/libs.tech/xschem so _pdk_xschem_dir() (xschem.py:47-54) resolves the sg13g2_pr/* refs; and vendor the xschem-share devices/ library, then set XSCHEM_LIBRARY_PATH (honored at xschem.py:33-36) on the backend (compose.yaml backend environment + Dockerfile ENV) pointing at both the library root and its devices/ subdir so devices/* refs resolve without installing the xschem binary.
(2) Alternatively/additionally, ship a self-contained sg13g2_pr/ and devices/ symbol set inside each example's own xschem/ dir so the base-.sch-dir search root resolves them with zero env/PDK dependence.
Also consider surfacing PDK-missing degradation in the Schematic view (per the env_probe pattern used elsewhere) instead of silently rendering all "?". Do not implement here.

### BUG-02 · Score Shaping aggregate F(x) reflects only the selected spec, not all configured specs

- **Area:** Score Shaping
- **Location:** [ui/src/components/tabs/ScoreShapingTab.tsx:70](ui/src/components/tabs/ScoreShapingTab.tsx#L70) (call site); [ui/backend/services/score_service.py:46-52](ui/backend/services/score_service.py#L46-L52),75-76 (aggregate exclusion)
- **Severity:** 🟠 major · **Confidence:** high
- **Symptom:** In the Score Shaping tab, only the currently-selected spec contributes to the aggregate score. The per-spec breakdown table shows "—" for current value, sigmoid P̂, and linear P̂ on every non-selected spec, and the "F(x) aggregate" footer (and the "dominant spec" callout) reflect only the one selected spec instead of the full multi-spec objective. Changing the spec dropdown changes which single spec is scored rather than scoring all of them together.
- **Root cause:** The frontend only ever sends a one-key metric vector. In ScoreShapingTab.tsx the component keeps a single `selectedSpec`/`metricValue` (lines 27-28); the effect at lines 84-86 runs `computeScore(selectedSpec, metricValue)`, and `computeScore` (lines 63-82) calls `api.computeScore(yamlPath, { [specName]: value }, specName)` — a dict with exactly one key (lines 70-74). There is no other `computeScore` call site (grep-confirmed: only ScoreShapingTab.tsx:70 and the api.ts:67 definition). On the backend, `compute_score` (score_service.py) iterates ALL enabled specs (`enabled_targets()`, line 33; loop line 39), but for any spec where `metric_values.get(spec.name)` is None (line 40 → branch line 46) it writes a null per-spec placeholder and `continue`s (lines 47-52), so `total_linear`/`total_sigmoid` (lines 75-76) accumulate only the single supplied spec, and `aggregate` (line 103) is `{-total_linear, -total_sigmoid}` over that one spec. The defect is purely frontend: the API client signature (`metric_values: Record<string, number>`, api.ts:69) and backend `ScoreRequest` (`metric_values: dict[str, float]`, score.py:27) already accept a full dict.
- **Fix direction (not implemented):** In ScoreShapingTab, maintain a per-spec value map keyed by spec name (each entry defaulting to its `target`), and on each debounced POST /api/score send the full vector `{ spec.name: currentValue }` for every entry in `enabledSpecs`, passing `selected_spec` only to drive the highlighted penalty curve. No backend change needed — score_service already sums all non-None specs into the aggregate and emits per-spec rows for each. This is exactly the unchecked TODO.md §3 "Multi-spec value panel" item ("a single debounced POST /api/score fires with the full vector of current values and returns per-spec and aggregate penalties in one shot"). Do NOT implement.
